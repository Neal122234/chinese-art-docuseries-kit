# 一座馆、两个大展厅：结构方案与引擎缺口

2026-09-27 · 只读代码写成，没有改任何文件。
读过的代码：`art-history/app`（index.html、js/core.js、tools/export_static.py、HANDOFF.md 末尾）、`art-history/deploy/deploy.sh`、`exhibit-kit/engine`（README、app/js/API.md、app/js/core.js、app/index.html、exhibit.example.json、tools/stage_publish.py、deploy/）。

## 0. 现状（决定方案的几个事实）
- 西方厅（艺术的演进）跑的是 **art-history 自己那份 core.js**（464 行，房间 id、时代名写死在文件顶部）。中国厅会用 **exhibit-kit 引擎**（`new_exhibit.sh` 生成的 core，房间和措辞读 exhibit.json）。所以是两份不同的核心。给一边加的功能，要手工移植到另一边。
- 两份 core **都没有深链接**：没有读 `location.hash`，也没有用 `history`（已 grep 核实）。现在只能从入口"点亮火光"进，然后从第一厅开始播。点门厅里的某一厅就进那一厅，这个功能两边都得新加。
- 西方厅现在的发布：`deploy/dist` 在站点根目录，586 个文件，193 MB，所有路径都是相对的（`rooms/…`、`js/core.js`、`fonts/fonts.css?v=…`）。只有 canonical、og:url、og:image 和 404 页里的"回到入口"写了绝对网址 `https://art-in-motion.pages.dev/`。`_headers` 里的规则写死了根路径（`/rooms/*`、`/audio/*`、`/fonts/*`）。
- `art-history/deploy/deploy.sh prod` 会把整个 dist 部署到 Cloudflare 项目 `art-in-motion` 的根目录，再用 `rsync --delete` 同步到 GitHub 镜像。记忆和 HANDOFF 里写的日常做法就是"直接 deploy.sh prod"。**合馆之后如果还有人照老办法跑一次，门厅和中国厅会被整个覆盖掉**（见 B5）。
- 引擎的发布规则（`stage_publish.site_files()`）：只发布 site.html 里 `src=` 引用的文件、已发布厅的 `rooms/<id>/`（跳过 `src/`、`_*`、`.*`）和 audio 清单里的文件。**theme.css 里 `url()` 引用的纹理图、`app/fonts/` 这类本地字体目录都不会被发布**（C4、C6 要用到）。

## B. 两个大展厅合成一座馆

### B1. 门厅长什么样（推荐：双列对照 + 同时期连线 + 年份尺）
我先试了"两条按真实年份对齐的时间线"。把西方 17 个厅和一份示意用的中国朝代表放到同一根分段线性的年份轴上（每段宽度按跨度的 0.35 次方算，已经大幅压缩了史前），结果西方从印象派到当代共 8 个厅只占总宽的 13%，每厅 1.2–1.9%。门厅宽约 1300 px 时，每厅只有 16–25 px，放不下字。换成纯线性或对数轴更糟。**所以不推荐真实比例的年份轴。**

推荐的门厅：
- **两列（或两行）各自等距排厅**，顺序与各自展厅的时间线一致：中国 11–14 个厅，西方 17 个厅加尾声。每厅是一块墙色的色块，悬停时显示挂的那件作品的小图、厅名和年代。
- **同时期连线**：两列之间用细墨线把年代重叠的厅连起来。例如巴洛克（c. 1600–1750）连到明、清；印象派（c. 1867–1886）连到清。连线就是"同一时期东西方各在哪一厅"的答案，比压扁的年份轴好读。
- **年份尺（有手感的部分）**：一方镇纸沿年代拖动，带惯性和阻尼，会吸附到厅的边界上。拖到哪一年，两边对应的厅就亮起来，连线变深，角落里的年份数字跟着走。例子：拖到 1113 年，中国一侧是北宋（《千里江山图》，1113 年，年份依 THEMES.md，待核查），西方一侧是中世纪（c. 500–1400）；拖到 1872 年，是清和印象派（《日出·印象》1872）。
- **点哪厅进哪厅**：点色块跳到 `west/#baroque`、`china/#<id>`；点展厅名从这个展厅的第一厅开始。
- **窄屏（390 px）**：两列竖排，中国在左、西方在右，连线在中间，年份尺改成上下拖。不做横向滚动。
- **门厅不出声**，不需要"点亮火光"那一步，因为声音要等进了展厅以后由展厅自己的入口解锁（见 B4）。
- 门厅的数据由构建脚本生成：从两个展厅的 room.json 读 `zh`、`yrs`、主图，再加一份 `museum.json` 给出每厅的数值年代（`from`/`to`）。现在的 `yrs` 是给人看的字符串，比如 "c. 40,000 – 10,000 BCE"，不能直接拿来算。尾声不上连线，放在列尾。缩略图生成 480 px 的 webp，放在门厅自己的目录里，不要直接引用 2400 px 的 main.webp。

### B2. 网址结构：三种做法
| | A. 根目录做门厅 + `/west/` + `/china/`（**推荐**） | B. 根目录仍是西方厅 + `/lobby/` + `/china/` | C. 新域名（新 pages.dev 项目） |
|---|---|---|---|
| art-in-motion.pages.dev | 打开是门厅，再点一次进西方厅。老链接不会失效，只是多一步 | 完全不变 | 不变（西方厅还要继续往这里部署一份） |
| GitHub 镜像 neal122234.github.io/art-in-motion/ | 同左，变成门厅，西方厅在 `/art-in-motion/west/` | 不变 | 不变；新馆要不要镜像，需要新建公开仓库（先问用户） |
| 已分享的卡片（微信等缓存的 og 图） | 仍显示西方厅的图，点进来是门厅，可以接受 | 不变 | 不变 |
| 结构语义 | 馆 > 两个展厅，清楚 | 中国厅挂在西方厅的站点下面，门厅不在正门 | 最干净，但老链接的访客看不到中国厅，除非西方厅里加外链 |
| 维护 | 一个 CF 项目、一个镜像 | 同 A | 西方厅要部署到两个项目，镜像两份，SEO 内容重复 |
| 改动量 | 西方厅导出时把 `--site-url` 改成 `…/west/`；合并脚本 | 合并时要避开西方厅根目录的文件（`index.html`、`404.html`、`_headers`、`share.jpg` 都会冲突） | 新建 CF 项目（和镜像仓库） |

**推荐 A**，理由：
1. "Art in Motion / 艺术的演进"这个名字本身就适合当馆名，域名不用换。两个大展厅可以叫"西方艺术"和"中国艺术的演变"（命名由用户定）。
2. 现在没有任何深链接，所以老链接只有根目录一个。A 不会让任何已分享的链接失效，只是多点一次。
3. 两个展厅的路径都是相对的，而且已经在镜像的子路径 `/art-in-motion/` 下验证过能用，挪到 `/west/` 不需要改代码。
4. 西方厅导出时要做的事：`--site-url https://art-in-motion.pages.dev/west/`，于是 canonical 和 og 都指向 `/west/`；404 页的"回到入口"指回门厅。

A 要注意的地方：
- `/west` 不带斜杠时，Cloudflare Pages 和 GitHub Pages 都会重定向到 `/west/`，相对路径能正常解析。门厅里的链接一律写成带斜杠的 `west/`。
- 根目录**必须有 404.html**。Cloudflare Pages 在顶层没有 404.html 时会按单页应用处理，所有缺失的路径都返回 index.html，check_static 就查不出漏发的文件。两个展厅各自的 404.html 留在 `/west/`、`/china/` 下面，CF 会用离请求路径最近的那一个（依据是 CF 文档中的 Not Found 行为，改版前再核对一次）。
- 如果用户不想让老链接有任何变化，退而求其次用 B。C 只在用户想要新馆名、新域名时才考虑。

### B3. 两个展厅共用什么
- **门厅**：只有一个。每个展厅左上角的标志（`.mark`，现在是纯文字）改成链接 `../`，写"展览馆"或馆名，入口页也放一个小的"回门厅"。
- **字体**：两边都用 Noto Serif SC（思源宋体的 Google 版）。自托管的 woff2 按内容哈希命名，同一个切片在两个展厅里文件名相同。可以在合并时把两边的 `fonts/` 去重到根目录 `/fonts/`，再改写两份 fonts.css 的 `url()` 指到 `../fonts/`，访客从西方厅走到中国厅就不用重新下载字体（**建议**，1–2 小时，不急）。中国厅另加楷体（见 C6）。
- **界面约定**：按钮、空格和 ←→ 的键位、阅读面板结构、查看器，两边已经一样（引擎就是从西方厅抽出来的）。
- **音频不共用**：每厅的音乐、音效 sprite 各自打包。两个展厅是两个页面，AudioContext 不能跨页面。界面音（ui-open 等）可以用同一批文件，但节省很少，不值得为它耦合两个项目。
- **入口的"那一下"各用各的**：西方厅是点亮火光，中国厅建议是按下一方印（`gate.markHTML` 放印章 SVG，文案"按下这方印，进入展厅"）。

### B4. 展厅之间怎么互相跳
1. **深链接 `#<房间id>`（两边都要加）**：打开 `china/#song` 时，入口文案改成"进入 · 宋"。点下以后调用 `go(idx)`：播放进入这一厅的转场（这正是那个"发现"的时刻），然后继续自动轮播。进厅时用 `history.replaceState` 同步 hash，这样刷新和分享都停在当前厅，而且不会刷满历史记录。另加 `hashchange` 监听，改 hash 时调用 `jump`。没有 hash 时行为和现在一样，check_static、分享截图都不受影响。
   引擎约 30 行，移植到西方厅的 core 约 30 行，还要回归测试：入口、跳过开场、←→、share.jpg、check_static 18 厅。
2. **阅读面板里的"同一时期"**：由门厅构建时算出的重叠关系注入展厅（`exhibit.json` 的 `siblings: {label, url, rooms:[{id, zh, from, to}]}`），引擎在阅读面板末尾加一行，比如"同一时期 · 中国：明 →"，点了跳到 `../china/#ming`。这是**建议**，引擎加 1–2 小时，西方厅移植 1 小时。
3. **尾声**：西方厅尾声的提示和 s-atlas 加一个"去中国艺术的演变"。中国厅最后一厅同理。
4. **跨展厅转场**（西方尾声直接转进中国第一厅）：两个展厅是两个页面，做不了真正的连续转场。要做只能合成一个页面，那就等于重写，**不建议**。

### B5. 构建和部署怎么合并（推荐：两个 app 各自导出，再拼进一个 dist）
不要把两个 app 合成一次构建。西方厅跑的是它自己分叉出来的 core，有 18 个像素级精确交接的转场，把它迁到引擎上至少要 1–2 天，还要全量回归，现在不值得冒这个险。

新建一个馆级目录（例如 `~/claude-projects/museum/`，名字待定）：
```
museum/lobby/        index.html、lobby.js、museum.json（两个展厅的厅序与数值年代）、build_lobby.py（生成缩略图、连线数据、siblings）
museum/deploy/       deploy.sh  → dist/
dist/index.html      门厅        dist/404.html   门厅风格的 404        dist/share.jpg  门厅分享图
dist/west/           art-history 的导出（export_static --out dist/west --site-url https://art-in-motion.pages.dev/west/）
dist/china/          china-art 的导出（export_static --out dist/china --site-url …/china/）
dist/_headers        合并：各展厅的规则加上前缀（/west/rooms/*、/china/fonts/* …），删除子目录里的 _headers
dist/.nojekyll       给 GitHub Pages
```
`museum/deploy/deploy.sh prod` 的步骤：
1. 两个展厅各自在自己的构建锁下 pack_sfx 和导出（EH_UPTO 各自配置）。
2. build_lobby 生成门厅。
3. 合并 `_headers`，去掉子目录的 `_headers`、`.nojekyll`。
4. 用 check_static 检查 `/west/`、`/china/`（它本来就支持子路径），再检查门厅：0 外部请求，所有链接和缩略图都能打开。
5. `wrangler pages deploy dist --project-name art-in-motion`。
6. rsync 到镜像仓库。
7. 两个展厅各自提交源码备份。

**必须同时做的防护**：把 `art-history/deploy/deploy.sh` 改成转调馆级 deploy.sh（或者直接报错退出），同步改 HANDOFF 和记忆里"直接 deploy.sh prod"的说法。否则老命令会把整个站点覆盖成只有西方厅。中国厅自己的 `deploy.sh review` 可以留着出预览，但要配一个独立的 CF 项目名，不能是 art-in-motion。

容量（量级估计，上线前按官方文档复核）：
- Cloudflare Pages 单文件 < 25 MiB，每次部署的文件数有上限（免费版文档写的是 2 万）。现在 586 个文件，加上中国厅也远低于上限。
- GitHub Pages 发布站点上限 1 GB。西方 193 MB，中国厅（手卷切片偏大）估计 150–300 MB，合计仍在 1 GB 以内。
- 镜像仓库每次部署都会把二进制文件的变化提交进历史，而 protect-main 禁止强推，历史会一直变大。长期是个隐患，现在不用处理。

工作量（agent 时间，可以 2–3 个 agent 并行）：
| 项 | 时间 |
|---|---|
| 深链接、标志链接、siblings（引擎 + 移植西方厅 + 回归） | 5–6 h |
| 门厅页（设计、年份尺、缩略图、窄屏、layout_lint） | 4–6 h |
| 馆级 deploy（拼装、_headers、404、三处检查、镜像、老脚本防护） | 3–4 h |
| 切换上线与核对 | 1 h |
| **合计** | **约 1.5–2 个 agent 日，并行后约半天墙钟时间** |

建议等中国厅的样板厅被用户认可以后再切换网址。在那之前，门厅里的中国一列显示"布置中"。

## C. 中国艺术对引擎的缺口
先算清楚现状：1389×713 下，挂作品的区域左边界 = 标题列右缘 + 32 ≈ 266 px，右边界 = 1389 − 展签宽 256 − 70 = 1063 px，所以宽 797 px；上下是 64 到 563，高 499 px。
- 《清明上河图》纵 24.8 cm × 横 528.7 cm（故宫出版社书目页 dpm.org.cn/journal_detail/239215.html），长宽比 1:21.3。按现在的挂法是 **797 × 37 px**，手机 390 宽只有 **358 × 17 px**。
- 《千里江山图》纵 51.5 cm × 横 1191.5 cm（故宫名画记 m-minghuaji.dpm.org.cn），长宽比 1:23.1。现在的挂法是 797 × 34.5 px。

另外 `paintArt` 把整幅图画进一张画布，宽度上限 2600 设备像素；查看器、放大镜、对比、调色板也都用整张 `main.webp`（STANDARDS 要求长边 ≤ 2400）。换成手卷，长边 2400 px 时高只有 113 px。**整个"一张图完整挂在一个矩形里"的假设对手卷不成立**，要在引擎层解决。

| # | 缺口 | 改哪里 | 工作量 | 风险 |
|---|---|---|---|---|
| 1 | 手卷：窗口挂法、切片、拖动卷动、自动展开 | **engine**（core 的挂法/交接/查看器 + build/strict + 切片工具） | 1.5–2.5 天 | 高 |
| 2 | 立轴：很高很窄 | engine（复用 #1 的纵向窗口）+ 装裱内边距 | +0.5 天 | 中 |
| 3 | 竖排文字 | 主要是项目内 theme.css + DESIGN-RULES；engine 加 tx 竖排规则和画布竖排助手 | 0.5–1 天 | 中 |
| 4 | 装裱画框 | engine 支持四边不等的内边距、发布主题素材；样式写在项目 theme.css | 0.5–1 天 | 低–中 |
| 5 | 印章 / 题跋图层 | 项目内展项 + 数据；引擎只提供手卷偏移接口（#1 的一部分） | 每个展项 0.5–1 天，查资料是大头 | 低 |
| 6 | 字体自托管（宋体、楷体） | engine 的 export 支持本地字体目录；项目 exhibit.json | 2–4 h，加竖排标点实测 30 分钟 | 低–中 |
| 7 | 每厅停留时长 | engine（room.json `hold`） | 0.5 h | 低 |

### C1. 手卷（最大的一项，建议先做这个样板）
**挂法："长案"横带**
- 手卷厅用新的布局模式 `band`：作品区从标题列右边一直伸到右边距，展签改放到带子下面（和中屏布局一样左对齐）。
- 1389×713 下，带宽 1087 px。带高取 300 px 左右时：
  - 《清明上河图》每厘米 12.1 px，一次看到约 90 cm（全卷的 17%），全卷 6,395 CSS px。
  - 《千里江山图》每厘米 5.8 px，一次看到约 186 cm。
- 手机竖屏：带子 358 px 宽，长宽比取约 1.2。手机横屏：473 × 258，约 1.8。
- 带子下面画一条**全卷缩略条**：1087 px 宽时，《清明上河图》整卷高 51 px，足够看出整体构图。条上框出当前窗口的位置，拖这个框就能快速走动。这条缩略条同时回答了"卷有多长"。

**看法**
- **从右往左展开**：卷首在右，越往后看画面内容越往右滑。
- **停留时自动慢慢展开**：room.json 写 `tour:[{x, t, note}]`，可以在关键段落停顿，每个 note ≤ 18 字，要过核查。停留时长按厅设（#7），例如 40–60 秒。
- **手动**：观众一动手，自动展开就暂停。横向拖动带惯性和阻尼；触摸板横向滚动、shift + 滚轮也能卷。←→ 仍然归引擎管（换厅），不能占用。手机上从距离边缘 20 px 以内开始的拖动不接管，避开 iOS 的返回手势。
- 查看器（放大查看）也要能按切片平移和缩放。

**数据与切片**
- `art: {kind:"handscroll", img:"main.webp"(代表段，给对比、调色板、分享用), w, h, scroll:{H, W, tiles:"scroll/", tileW, levels:[1200, 2400], start, tour}}`。
- 切片工具 `tools/tile_scroll.py`：用 PIL 把原图切成两级 webp。
  - 1200 高的一级：约 25,600 × 1200 px，约 30.7 MP，按经验估 6–10 MB，需实测。
  - 2400 高的一级给查看器放大用。
  - 切片放在 `rooms/<id>/scroll/`，这个目录会被自动发布。
- 内存：30.7 MP 全部解码成 RGBA 约 123 MB，iOS Safari 扛不住。所以只解码窗口前后各两屏的切片，其余释放。
- `build --strict` 改成检查切片是否齐全、尺寸是否一致。

**转场契约的变化**
- `ctx.to.rect` = 窗口矩形，`ctx.to.image` = 起始窗口的快照（init 时用切片合成一张离屏画布）。
- `ctx.from.image` 改成**进下一厅那一刻对挂着的画布拍的快照**。观众可能把卷拖到了任何位置，p = 0 必须和他看到的一致。这个改法对普通厅也成立，而且更稳。
- THEMES 里"上一厅的最后一段就是这一卷的起首"这个点子，要靠这个快照才能做对。
- rest() 画在作品上的东西要跟着偏移走，所以提供 `ctx.to.offset`。

**MVP 顺序**：窗口挂法 + 拖动 + 自动展开 + 快照交接（约 1–1.5 天）→ 缩略条 → 查看器和放大镜按切片工作（约 0.5–1 天）。
风险在于改的是 core 的挂画、交接和查看器，**必须用 demo 两厅加中国样板厅做全量回归**（交接像素差、motion、cost、layout_lint 全尺寸矩阵）。西方厅用的是另一份 core，不受影响。

与展项的分工：引擎只负责"挂着的卷能看、能拖"。THEMES 里"展开一卷"的展项（两只手各拖一头，卷起右边、展开左边，卷得快画会跑）是项目内的 `s-scroll.js`，有自己的卷轴物理手感，可以复用切片。

### C2. 立轴
- 按现在的挂法，1389×713 下作品区高 499 px：画心 1:2 时宽 250 px，还行；画心 1:3 时宽 166 px；加上完整装裱（天头、地头）往往到 1:4 以上，只有约 125 px 宽，看不清。
- 做法 1：复用 #1 的窗口机制，改成纵向（`kind:"hangingscroll"`，自动从上往下走），右侧画一条竖向缩略条。
- 做法 2：墙上只挂画心加一圈简化的装裱（隔水 + 短天头 + 短地头，比例做了示意性压缩，要在展签或说明里写明）。完整装裱只在查看器里看全。
- 做法 3：顶部控件和作品不重叠时，允许高幅作品上下各多用约 60 px（`t` 从 64 降到约 24）。
- 推荐 1 + 2。如果原件照片没有拍到装裱，就只挂画心，不去伪造装裱。

### C3. 竖排文字
**推荐的范围**
- 竖排：厅名（`.era h1` 已经是 vertical-rl）、一句话简介、引文（题跋、画论）、展签（可选）。
- 阅读面板的长文保持横排。原因：面板竖排会变成从右往左横向滚动，和现在的 overflow-y、上下渐隐遮罩、`touch-action: pan-y`、layout_lint 的判定全都冲突，风险高，收益小。要做的话单独立项。

**写法**
- `writing-mode: vertical-rl`，`text-orientation: mixed`，`line-break: strict`（避头尾在竖排里同样适用）。
- **数字**：年份在内容里写成汉字（"公元一一一三年"），这是竖排的通行写法，建议写进 DESIGN-RULES。其余一到两位的数字，由 tx() 包成 `<span class="tcy">`，用 `text-combine-upright: all`。`text-combine-upright: digits` 的浏览器支持很差，不要用。
- **标点**：靠字体的 vert 特性把 ，。《》 换成竖排字形。Noto Serif SC 是按大陆规范做的。竖排里的引号，国标 GB/T 15834—2011 的规定需要核实条款（通常的做法是改用直角引号﹁﹂）。这和横排"不用「」"的规定不矛盾，但要在 DESIGN-RULES 里写清楚竖排例外。
- **风险**：Google Fonts 切片版是否保留了 vert、vrt2 和竖排度量没有验证过。要在 1389×713 和手机上各渲染一行"，。、《》“”——……1113"，和系统宋体对比，约 30 分钟。如果不保留，就走 C6 的自行子集化。
- **画布上的竖排**：Canvas 2D 不支持竖排。转场字幕需要引擎提供助手 `ctx.u.vtext(g, str, x, y, size)`：逐字排版，标点换成竖排表现形式（U+FE10–FE19，︽︾ 等）。引擎约 1–2 小时。

**改哪里**：项目 theme.css + DESIGN-RULES 的竖排一节 + 引擎的 tx() 竖排分支与 vtext。改完 index.html 或 core 后按 STANDARDS 跑全尺寸 lint 矩阵。

### C4. 装裱画框
- **现状**：画框内边距 `FRAME_PAD` 只支持四边相等（`[窄屏, 宽屏]` px），`rectFor` 按对称内边距居中。装裱天头长、地头短，隔水是左右（手卷）或上下（立轴）的窄条，都是不对称的。
- **引擎**：`frames` 支持 `{"mount":{"t":.18,"b":.09,"l":.03,"r":.03,"unit":"art"}}`，即按作品尺寸的比例给四边，同时保留 px 写法。rectFor、hang 和 CSS 的 `padding` 改成四个变量。另外让 stage_publish 发布 `app/theme/` 目录，否则 theme.css 里引用的绫绢纹理图不会上线。约 3–4 小时。
- **项目**：theme.css 写 `.frame.f-mount::before`（立轴：天头、惊燕、隔水、地头、轴头用 `::after` 突出两侧）和 `.frame.f-scroll`（手卷：包首、隔水）。绫绢色取装裱实物，纹理用公有领域扫描图，不用程序噪声。约 3–4 小时。
- 天头地头的比例常见约 3:2 到 2:1，这是经验说法，没有出处前不要写进展签。
- 转场不受影响：p = 1 只画画心；画框是 DOM，由 `ctx.ui.deco` 控制淡入。

### C5. 印章 / 题跋图层
- **数据**：room.json 的 `special.marks:[{x,y,w,h(按作品归一化), kind:"seal"|"colophon", who, when, text, src}]`。每一方印的释文、归属、年代都要有出处（馆方的印章清单或著录），查不到的写"未释"，不猜。
- **展项**（项目内的 `s-seals.js`）：按 `api.artRect()` 对齐叠加。拖动年代尺，印章按年代一方方出现，这也是"盖上一方印"转场点子的互动版。手卷的印章在切片坐标上，需要 #1 提供 `api.scroll.offset()` 和 `api.scroll.to(x)`。
- **规则冲突**：STANDARDS 规定 `ctx.tool='special'` 时 rest() 不在作品上画。印章叠加由展项自己的画布负责，不走 rest，所以不冲突。
- 真正的成本在查资料：一件法书上的印可能有几十方。

### C6. 字体（大陆访问，0 外部请求）
2026-09-27 实测 Google Fonts css2 接口：
| 字体 | 结果 |
|---|---|
| Noto Serif SC（思源宋体的 Google 版） | 有，400 字重 101 个切片 |
| LXGW WenKai TC（霞鹜文楷繁体版） | 有，115 个切片 |
| Ma Shan Zheng、Zhi Mang Xing（书法风格） | 有，各 92 个切片 |
| LXGW WenKai（简体标准版） | 没有，请求返回错误页 |

以上都是 OFL。简体版霞鹜文楷在 npm 上有 `lxgw-wenkai-webfont` 和 `lxgw-wenkai-screen-webfont`，都是 1.7.0，带切片 CSS（jsDelivr 数据接口核实过存在；许可以上游仓库为准，下载前再确认）。

- **现在就能用**：exhibit.json 的 `fonts.css` 写 Google css2 地址，导出时自动自托管（西方厅就是这样，fonts/ 共 6.5 MB）。浏览器按 unicode-range 只下载用到的切片，子集化这件事在效果上已经做到了。
- **引擎缺口**：
  - export 只认 `fonts.gstatic.com`，所以简体版霞鹜文楷（npm 包）或自己子集化的字体没有路可走。要让 build 和 export 支持 `fonts.local`：`app/fonts/*.css + woff2` 原样发布，check_static 核对字体族。约 2 小时。
  - 繁体版的字形按台湾标准，简体字的覆盖和字形是否合适要实测。
- **自己子集化**（按全部文字抽用字，每个字重一个文件，竖排特性和度量有保证）：需要 fontTools 加 brotli，本机现在**都没装**（`import fontTools` 和 `import brotli` 都失败）。装它们会改动用户的 Python 环境，先问用户。另一个代价是：每加一厅字就变，每次导出都要重新子集化。只在 C3 实测发现切片丢了竖排特性时才走这条路。
- **书法字体**：标题要用书法，优先用原迹集字（真实作品里的字，写明出处）。Ma Shan Zheng 这类字体是现代人仿写的，只能当装饰，不能冒充古人的书迹。

### C7. 其他小缺口
- **每厅停留时长**：现在 HOLD 是全局的（exhibit.json `hold`）。手卷和立轴厅要更长，需要 room.json 的 `hold` 覆盖。约 0.5 小时。
- **预渲染视频**：墨晕、题跋按笔顺写出这类转场用预渲染的 mp4，stage_publish 已经支持 .mp4、.webm、.bin，不用改。
- **声音**：古琴、琵琶、箫的公有领域或自由许可录音很少，作品和录音的许可都要核实。这不是引擎的事，但要尽早开始找。
- **图源核实**：本次查 Wikimedia Commons API 时被限流（HTTP 429，可能是并行的 agent 太多），手卷原图的像素尺寸留给图源 agent 核实。决定切片级数前要知道原图有多高：低于约 1200 px 时，查看器的第二级就没有意义。
